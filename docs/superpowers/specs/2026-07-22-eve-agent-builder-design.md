# Eve Agent Builder — Design

Date: 2026-07-22
Status: Approved direction (template source: live `apps/eve`; config depth: deep; builder home: new `apps/builder`)

## Goal

A new `apps/builder` web app where a visitor configures their own Eve agent —
name, personality, instructions, individual tools, channels, schedules — pastes
their keys, and clicks one button. The builder deploys a fully working copy of
the Eve agent app (chat UI + agent runtime) into **their** Vercel account using
their Vercel token. No GitHub, no CLI, no manual setup.

## Why this is feasible

- `withEve` bundles the agent runtime, web chat, crons, and sandbox into a
  single Next.js project — one Vercel deployment, so "deploy an agent" means
  "deploy one project".
- Models route through the deployer's own Vercel AI Gateway via OIDC. No model
  provider keys are needed; model usage bills to the user's Vercel account.
- Every Postgres-backed store in the app self-creates its tables
  (`CREATE TABLE IF NOT EXISTS`), so a bare Neon connection string is enough.
- The Vercel REST API supports the whole pipeline with a personal token:
  create project, upsert env vars, create a deployment from inline source
  files (Vercel builds remotely), poll status.

## Architecture

```
eveclaw monorepo
├── apps/eve        # the real agent app — also the deploy template (source of truth)
└── apps/builder    # wizard UI + deploy pipeline (its own Vercel project)
    ├── app/                  # Kumo-styled wizard pages
    ├── app/api/deploy        # POST: create project + env + deployment (returns ids)
    ├── app/api/deploy/status # POST: poll deployment state (stateless, token per call)
    ├── lib/vercel-api.ts     # typed client for the Vercel REST endpoints we use
    ├── lib/manifest.ts       # feature → file map, exclusions, completeness rules
    ├── lib/assemble.ts       # read apps/eve, apply transforms, emit deploy files
    ├── lib/instructions.ts   # generate instructions.md from wizard config
    └── lib/schedule-codegen.ts # emit custom defineSchedule files
```

### Template = live `apps/eve`

The builder assembles the deployment from `apps/eve` source at deploy time.
No checked-in copy to drift. Mechanics:

- **Exclusions:** `.env*`, `.eve/`, `.next/`, `node_modules/`, `.turbo/`,
  `.output/`, `PLAN.md`, `AGENTS.md`, `CLAUDE.md`, `scripts/`, `.agents/`,
  `*.tsbuildinfo`, `.vercel/`.
- **Transforms:**
  - `package.json` — rename to the user's agent slug (dependencies are
    already self-contained; nothing else changes).
  - `agent/instructions.md` — replaced wholesale with wizard output.
  - Feature pruning — unselected features remove their files (map below).
  - Custom schedules — generated `agent/schedules/custom-*.ts` files added.
- **Bundling:** the builder's deploy route needs `apps/eve` source at runtime;
  use Next `outputFileTracingIncludes` pointing at `../eve/**` (fallback: a
  prebuild script that snapshots a JSON manifest).
- Deployment payload is inline base64 files via `POST /v13/deployments`
  (source is well under inline limits; `/v2/files` SHA upload is the escape
  hatch if it grows).

claimed by exactly one feature (or core/exclusions), so new tools added to the
personal app fail CI until the map is updated.

### `apps/eve` templatability refactor (prerequisite)

1. **Owner name:** `channels/hooks.ts`, `schedules/reminders.ts`, and
   `schedules/memory-consolidation.ts` hardcode "Micky". Introduce
   `OWNER_NAME` env (fallback `"Micky"`); generated instructions use the
   wizard's owner name.
2. **Feature-aware UI:** manage page tabs and related API routes currently
   assume every feature is configured. Add a tiny `/api/features` route that
   reports availability derived from env presence (`SUPERMEMORY_API_KEY` set →
   memory tab on, etc.); the manage page hides unavailable tabs. This also
   improves the personal app (graceful degradation instead of failing tabs).
3. Sweep for any remaining personal strings in the web UI (none found in
   `app/`/`components/` today).

## Wizard flow (deep config)

1. **Connect Vercel** — paste token → validate (`GET /v2/user`), list teams
   (`GET /v2/teams`) → pick target team/personal scope. Link to Vercel's token
   page with scope guidance.
2. **Identity** — agent name (→ project slug), owner name, personality preset
   (assistant / coach / ops bot / blank) + freeform notes, default model
   (same catalog as the chat's model picker).
3. **Capabilities** — grouped tool picker with per-tool checkboxes (groups =
   feature map above). Dependencies auto-resolve: checking any receipt tool
   requires `DATABASE_URL` (already mandatory); checking memory tools adds the
   Supermemory key step, etc. Browser control, weather, dice are free toggles.
4. **Channels** — web chat (always on), Telegram (token, webhook secret,
   allowlist ids).
5. **Schedules** — optional list of custom recurring jobs: name + cron (UTC)
   + prompt. Each becomes a generated `defineSchedule` file that delivers into
   a web chat thread (same delivery path as reminders). Selecting any custom
   schedule therefore pulls `lib/web-thread-delivery.ts` and `lib/runs-db.ts`
   into the build even when the proactive feature is off. The runtime reminder
   system (created via chat) is separate and needs no builder config.
6. **Instructions** — the generator composes `instructions.md` from identity +
   selected features (sections mirror the current file: Identity, Style,
   Memory, Skills, Receipts, Capabilities, Proactive, Subagents). Shown in a
   raw markdown editor for full editing before deploy.
7. **Keys** — one form listing exactly the env vars the selection requires
   (see map). VAPID keys are generated server-side and never shown. Postgres
   URL field links to Neon's free tier.
8. **Review & deploy** — summary; the deploy button runs the pipeline and
   streams stage progress; ends with the live URL and a post-deploy checklist
   (open chat, enable notifications, connect Composio apps, DM the Telegram
   bot).

## Deploy pipeline

`POST /api/deploy` (single request, secrets in memory only):

1. Validate token; resolve team id.
2. Create project — `POST /v11/projects` (framework `nextjs`, name = slug;
   on 409 name conflict, surface and let the user rename or confirm redeploy
   into the existing project).
3. Generate VAPID key pair (`web-push`).
4. Upsert env vars — `POST /v10/projects/{id}/env?upsert=true` (targets:
   production, preview, development).
5. Assemble files (manifest + transforms + generated instructions/schedules).
6. Create deployment — `POST /v13/deployments` with inline files,
   `target: production`, `projectSettings.framework: "nextjs"`.
7. Respond with `{ projectId, deploymentId, url }`.

The wizard then polls `POST /api/deploy/status` (token + deploymentId from
client memory) every ~3s: proxies `GET /v13/deployments/{id}`, mapping
`QUEUED → INITIALIZING → BUILDING → READY | ERROR`. On `ERROR`, fetch build
logs via `GET /v3/deployments/{id}/events` and show the failing excerpt plus a
link to their Vercel dashboard. On `READY`, hit `https://<url>/eve/v1/health`
as a final smoke check. If a Telegram token was provided, call Telegram's
`setWebhook` pointing at the deployed channel route as a post-deploy step.

Redeploy/update story (v1): running the wizard again with the same project
name deploys a fresh build into the existing project (env upsert + new
deployment). Documented, not specially built.

## Secrets & trust model

- All keys travel in the deploy request body over HTTPS, are used for Vercel
  API calls in-handler, and are never logged or persisted. The builder has no
  database.
- The client keeps the token in memory (React state, not localStorage) for
  status polling; a page refresh forgets everything.
- Stated plainly in the UI: pasting a Vercel token grants broad account
  access; recommend a dedicated token. The upgrade path for a public product
  is "Sign in with Vercel" OAuth — out of scope for v1.
- Deployed agents inherit the template's auth posture: the eve channel and
  API routes are open (`none()`), matching the current personal app. The
  post-deploy checklist says so and points at Vercel Deployment Protection;
  a built-in login is a v1.1 candidate.

## Error handling

- Stage-tagged errors (`token`, `project`, `env`, `deploy`, `build`) so the
  wizard can point at the failing step with a retry that resumes (project
  creation is idempotent-by-name; env upsert is idempotent; deployment create
  is safe to repeat).
- Invalid cron expressions rejected at the schedules step (`cron-parser`).
- Manifest assembly failures (missing file, unclaimed tool) are build-time
  bugs surfaced by the completeness test, not runtime surprises.

## Testing

- Unit: manifest completeness (every `agent/` file claimed once), assemble
  transforms (snapshot of emitted file list + key file contents for a fixed
  config), instruction generator output per feature combination, schedule
  codegen validity (typechecks via `tsc` in a temp dir).
- Integration: `scripts/smoke-deploy.ts` deploys a minimal config to our own
  account with a real token from env, waits for READY, curls `/eve/v1/health`,
  then deletes the project. Run manually / pre-release.
- Manual: full wizard run deploying to a scratch Vercel account.

## Out of scope (v1)

- OAuth ("Sign in with Vercel") instead of pasted tokens.
- Auto-provisioning Neon or Blob via the Marketplace API (user pastes strings;
  Blob-dependent features simply stay off without a token).
- Managing already-deployed agents (fleet dashboard, config diffing).
- Custom domains, team billing guidance, usage analytics.
